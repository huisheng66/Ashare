## 项目深度分析（代码走查，无改动）

架构要点（后续改动需遵守）：
- URL 是唯一状态源：筛选/排序/视图全走查询参数，`lib/catalog-query.ts` 的 `parseCatalogFilters`（服务端）与 `catalogFiltersFromURL`（客户端）共用同一解析，禁止另起客户端状态。
- 数据层三层：`lib/catalog.ts`（React `cache` 请求级快照）→ `lib/store.ts`（4 个 JSON 文件 + SHA-256 旁车）→ `lib/json-store.ts`（按文件串行队列、tmp+fsync+rename 原子写、可选 .bak）。写路径只经 `updateCatalog`。
- 列表跨 RSC 边界只传 `toCatalogItem()` DTO（裁掉 body/tutorial/links/aliases，仅首张预览）。
- 搜索在 `lib/items.ts::searchSoftware`：NFKC 归一化 + 多词 AND + 字段打分 + 短语加成 + 稳定排序。

现状与坑（重要）：
- `data/store/catalog.json` 是 gitignore 的运行库，只在文件不存在时用 `data/software.ts`(30) + `data/samples.ts`(3) 灌种子。当前运行库 32 条、**不含 mineradio**，music 等 6 个新场景计数为 0 —— 改种子对已有部署无效，新增条目必须走后台或删 store 重建。

- `seedCatalog` 对 seed 与 samples 的 slug 未去重，目前无重复，加种子时需自查。
- 部署约束：单 Node 进程 + 持久盘；`/media/[...path]` 路由存在的意义是 `next start` 不发现构建后新增的 public 文件。

## 第八轮：精简流程与代码 + 安全加固（不录新条目）

#### 安全（本轮最重要）
- **check-links 的 --url 有 SSRF 缺口**（上一轮我加的，没限制目标）。候选地址若来自网页/投稿，脚本会去打 169.254.169.254、内网、file://，而这类脚本由 AI 自动执行。
- 修复：统一走 `scripts/_shared.mjs` 的 `safeFetch` —— 只放行 http/https、预解析 DNS 拒绝私有/保留/环回/组播段、`redirect:"manual"` **逐跳**校验。`--allow-private` **只放行第 0 跳**（否则测 localhost 会被 302 带进内网）。
- IPv6 位宽踩坑：`fe80::1` 第一版判成公网。正确是取首段前 16 位：`head & 0xfe00 === 0xfc00`（fc00::/7）、`head & 0xffc0 === 0xfe80`（fe80::/10）。用 16 个地址的用例表回归。
- **backup --keep 是 fs.rm -r**：此前只按目录名匹配就删。现在要求目录内有带 createdAt 的 manifest.json；归档用 `tar -tzf` 确认含 manifest，否则跳过。已用假目录验证会保留。
- 隐私：manifest 标出 feedback/blocks/inbox.json 并提示分享前剔除（恢复要完整，分享不需要）。
